  ### 2. RAG & ChromaDB Architecture (The Main Mechanism)

  The RAG system in rag_service.py and rag_service.py implements a 3-Layer AI Security Pipeline:

  1. Document Ingestion & Chunking (rag_service.py & splitter.py):
      • Uploaded .pdf, .docx, and .txt documents are loaded and split into text chunks (chunk_size=1000, chunk_overlap=200) using LangChain's      
      RecursiveCharacterTextSplitter.
      • Each chunk is stored in the local vector database (ai-service/chroma_db/) along with metadata such as { "source": filename, "role":        
      "<required_role>" }.
  2. Layer 1: Input Guardrails:
      • Before executing vector searches or calling the LLM, inputs are scanned for prompt injection or jailbreak keywords (ignore, override,      
      bypass, jailbreak, confidential). Malicious queries are blocked immediately without invoking the model.
  3. Layer 2: Secure RAG Retrieval via ChromaDB Metadata Filtering:
      • When a user asks a question, ChromaDB does not retrieve all relevant chunks across the database.
      • Instead, the retriever applies a Role-Based Metadata Filter:
        search_kwargs = {"k": 5}
        if role not in ["CEO", "Manager", "HR"]:
            search_kwargs["filter"] = {"role": role}

      • Chunks belonging to confidential categories (such as Salary Structure or CEO Compensation) are never retrieved from ChromaDB for lower-    
      privilege roles. The LLM only sees documents the user is explicitly authorized to view.
  4. Layer 3: Output Guardrails & Audit Logging:
      • Responses are checked for hallucinations or empty outputs, and user interactions (question, user role, retrieval status, timestamp) are    
      logged to the MySQL audit_logs table.

  ### 4. How Users Access Data in the RAG (Step-by-Step Flow)

    sequenceDiagram
        participant User as React Frontend
        participant Gateway as Node.js Backend
        participant DB as MySQL Database
        participant AI as Python FastAPI / RAG
        participant Chroma as ChromaDB
        participant LLM as Groq LLM

        User->>Gateway: POST /auth/login (email, password)
        Gateway->>DB: Validate credentials & get role
        Gateway-->>User: Return JWT Token & User Info
        User->>Gateway: POST /chat (question) + Authorization: Bearer <JWT>
        Gateway->>DB: Decode JWT & fetch User Role (CEO / HR / Employee / Intern)
        Gateway->>AI: Forward request { "question": "...", "user": { "role": "..." } }
        AI->>AI: 1. Check Input Guardrails (Prompt injection check)
        AI->>Chroma: 2. Search Vector DB with filter {"role": user.role}
        Chroma-->>AI: Return ONLY authorized document chunks
        AI->>LLM: 3. Prompt LLM with question + allowed chunks
        LLM-->>AI: Generated Answer
        AI->>AI: 4. Check Output Guardrails & log audit trail
        AI-->>Gateway: { "answer": "..." }
        Gateway-->>User: Display answer in UI

  #### Key Security Takeaway

  Because metadata filtering happens inside ChromaDB before the LLM is invoked, the AI never receives confidential text chunks for unauthorized    
  users. This prevents accidental data leaks or LLM prompt-injection overrides from exposing restricted documents.
